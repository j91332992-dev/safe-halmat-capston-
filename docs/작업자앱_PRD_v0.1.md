# HANMIR 작업자 앱 PRD v0.1

작성일: 2026-10-09 / 상태: 검토용 초안

## 1. 제품 목적

작업자가 자신의 안전모 상태와 안전 알림을 확인하고, 위험 상황에서 관리자에게 도움을 요청할 수 있는 모바일 앱을 만든다. 기존 관리자 앱과 동일한 서버를 사용하며, 작업자는 본인에게 배정된 정보에 접근한다.

핵심 질문은 세 가지다. “내 안전모가 연결되어 있는가?”, “내가 지금 알아야 할 위험은 무엇인가?”, “도움을 요청했을 때 실제로 전달되었는가?”

## 2. 현재 배경과 확인 범위

- 기존 frontend에는 관리자 로그인, 작업자 현황, 지도, 위험 이벤트, 장치 상태 화면이 있다.
- 기존 backend에는 장치 heartbeat, 위치, 음성 명령, 이벤트 및 통화 관련 코드가 있다. 작업자 전용 권한·API는 별도 구현 여부와 보안 검증이 필요하다.
- 신규 배선표 기준 안전모는 DFR1172 ESP32-P4/C6, OV5647 카메라, MAX17048, INMP441, MAX98357A, BNO085로 구성된다. UWB 태그는 P4 데이터선 없이 자체 경로로 위치를 전송한다.
- 사용자는 배선을 완료했다. MAX17048 단독 시험 코드는 작성됐으나 실물 동작 성공은 아직 확인되지 않았다. 카메라 시험에서 흑백이 나온 원인은 미확인이다.
- P4 계획 코드와 실물 검증 상태는 구분한다. 문서에 있는 전압 전송, 낙상 검출, 양방향 통화를 구현 완료로 가정하지 않는다.

근거: `docs/MAX17048_앱연동_계약.md`, `docs/MAX17048_점검_대화정리.md`, 기존 관리자 모바일 화면, 사용자가 제공한 신규 배선표 및 GitHub feature/mobile-safety-app-20261001 브랜치 확인 기록. 이번 초안은 로컬 코드와 앞선 확인 기록 기준이며 최신 원격 브랜치 전체 재검증 결과는 아니다.

## 3. 사용자와 사용 상황

대상은 현장에서 안전모를 착용하는 작업자다. 첫 버전은 Android 스마트폰을 기준으로 제안한다. 배포 방식과 최소 OS 버전은 구현 착수 전에 확정한다.

| 상황 | 작업자가 해야 하는 일 |
| --- | --- |
| 작업 전 | 본인·현장·안전모 배정과 연결 및 잔량을 확인 |
| 작업 중 | 본인 관련 위험·대피 안내를 확인 |
| 위험 발생 | SOS를 보내고 접수·관리자 확인 상태를 확인 |
| 연결 끊김 | 최신 상태를 확인할 수 없음을 알고 연락 수단 사용 |

## 4. 첫 버전 범위

| 우선순위 | 기능 | 요구사항 |
| --- | --- | --- |
| 필수 | 작업자 로그인 | 관리자가 등록한 작업자 계정으로 로그인. 서버가 본인·현장 범위를 결정 |
| 필수 | 홈 | 이름, 현장, 배정 안전모, 서버 연결, 안전모 연결, 잔량, 최근 수신 시각 표시 |
| 필수 | SOS | 지속해서 접근 가능한 큰 버튼. 길게 누르기 2초로 신고, 요청 상태 표시 |
| 필수 | 안전 알림 | 본인 관련 경고와 현장 공통 대피 안내 수신·상세·읽음 표시 |
| 필수 | 관리자 연락 | 현장에 등록된 연락처로 전화 앱 연결. 연락처 미등록 시 안내 |
| 필수 | 장치 상태 | AV 안전모와 UWB 태그 연결 상태를 개별 표시 |
| 후속 | 내 위치 | 본인 UWB 위치와 현장 구역 표시. 위치 최신성 함께 표시 |
| 후속 | 앱 내 음성 통화 | P4/서버/앱 오디오 통합과 실물 검증 후 제공 |
| 후속 | 작업 전 점검 | 상태 확인과 사용자 확인 항목 기록 |

첫 버전에서는 전 작업자 목록·영상 관제·위험도 편집·장치 원격 제어·인사/출퇴근 기능을 제공하지 않는다. 카메라와 음성 AI 분석은 기존 안전모/서버의 역할로 두고 앱은 검증된 결과를 표시한다.

하단 메뉴는 홈 / 알림 / 내 안전모 / 내 정보의 네 개로 제안한다. SOS는 로그인 후 주요 화면에서 접근할 수 있도록 고정한다.

| 화면 | 표시·행동 |
| --- | --- |
| 로그인 | 작업자 계정, 로그인 오류, 현장 서버 연결 안내 |
| 홈 | 본인·현장·안전모, 연결 상태, 잔량, 최근 경고, 관리자 연락, SOS |
| 알림 | 경고·대피 안내, 발생 시각, 대응 안내, 읽음/확인 |
| 알림 상세 | 내용, 현장 구역, 본인 관련 여부, 관리자 확인 상태 |
| 내 안전모 | 안전모와 태그 ID, 연결 상태, 최종 수신 시각, 배터리, 검증된 부품 상태 |
| 내 정보 | 작업자/현장 정보, 배정 장치, 담당자 연락처, 알림 권한, 로그아웃 |
| SOS 진행 | 전송 중·서버 접수·관리자 확인·실패 표시, 전화 연결, 오신고 정정 요청 |

## 6. 주요 동작 요구사항

### 6.1 로그인과 배정

계정은 관리자 등록 방식으로 시작한다. 작업자가 임의로 다른 작업자 ID를 선택할 수 없다. 앱에 표시하는 이름·현장·장치 배정은 서버에서 내려준다. 장치 미배정이면 “안전모 배정이 필요합니다”와 관리자 연락을 제공한다. 장치 배정 변경과 로그아웃 시 이전 작업자의 데이터와 알림을 제거한다.

### 6.2 연결과 배터리

휴대폰→서버 연결, 안전모→서버 연결, UWB 태그→서버 연결을 각각 구분한다. 휴대폰 인터넷이 연결됐다는 이유만으로 안전모 정상이라고 표시하지 않는다.

MAX17048 SOC를 안전모 배터리 %로 사용한다. 태그 배터리와 혼동하지 않는다. null·미수신·오류는 0%로 바꾸지 않고 “확인 불가”로 표시한다. 이전 값이 있으면 “마지막 확인 82%, 2분 전”처럼 최신성도 표시한다. 시뮬레이터 값은 데모 데이터임을 명시한다.

저전압 알림 초안은 SOC 20% 이하 주의, 10% 이하 충전 권고다. 현장 운영 기준에 따라 변경할 수 있어야 한다. 같은 상태에서 알림을 반복하지 않는다. 전압은 서버가 실제 값을 제공할 때 장치 상세에 표시하며 미구현 값은 생성하지 않는다.

정상 상태도 “위험 없음”으로 단정하지 않고 “현재 수신된 경고 없음”으로 표시한다. 오래된 데이터는 정상색만 남기지 않는다.

### 6.3 SOS

길게 누르기 시작 시 진행 표시와 진동을 제공하고, 2초 완료 전에 손을 떼면 전송하지 않는다. 완료하면 요청을 생성하고 서버 응답을 기다린다. 접근성 대안으로 명시적 확인을 거치는 신고 방식도 제공한다.

상태는 전송 중 → 서버 접수 → 관리자 확인으로 구분한다. 서버의 실제 확인 응답 전에는 성공으로 표시하지 않는다. 관리자 확인은 사람이 수행한 확인 기록이 있어야 표시한다. 같은 신고의 재시도는 같은 요청 ID를 사용해 중복 사건을 만들지 않는다.

전송 실패·서버 연결 불가 시 “신고가 전달되지 않았습니다”를 명확히 표시하고 재시도와 담당자 전화 연결을 제공한다. 연결이 없을 때 자동으로 구조가 요청됐다고 표현하지 않는다. 오신고 정정은 사건 이력을 삭제하지 않고 정정 요청으로 남긴다.

### 6.4 알림

본인 경고와 현장 전체 대피 공지를 구분한다. 알림을 열어 읽은 것과 관리자 사건 처리 완료를 구분한다. 동일 이벤트 ID는 한 번 표시하고, 변경된 상태는 같은 알림에 반영한다. 앱이 백그라운드여도 알림을 받을 수 있도록 모바일 푸시가 필요하다. WebSocket만으로 백그라운드 수신을 보장하지 않는다.

알림 권한 거부 시 홈에 안내한다. 앱 내 목록은 사용할 수 있어야 한다. 소리·진동은 사용자 OS 설정을 존중한다. 대피 경로는 실제 현장 데이터가 승인된 경우에만 제공한다.

### 6.5 위치와 개인정보

후속 지도 기능은 본인 위치만 기본 표시한다. 위치 없음·오래됨·측위 품질 불량을 표시한다. 스마트폰 GPS와 UWB를 혼동하거나 조용히 대체하지 않는다. 카메라 영상과 음성을 앱이 상시 수집하는 요구사항은 없다. 데이터 수집 목적·작업 시간·보관 기간은 현장 정책을 확정한 뒤 명시한다.

## 7. 서버 연동 요구사항

안전모·태그 → 기존 서버 → 작업자 앱의 구조를 사용한다. 첫 버전 앱은 MAX17048이나 P4에 직접 연결하지 않는다. 신규 BLE 연결이 이미 구현됐다고 가정하지 않는다.

| 필요한 계약 | 포함할 정보 | 상태 |
| --- | --- | --- |
| 작업자 인증/본인 정보 | 작업자, 조직, 현장, 배정 장치, 권한 | 작업자용 신규 설계/검증 필요 |
| 본인 장치 상태 | SOC, 마지막 수신, 온라인 상태, 태그 상태 | 기존 heartbeat 데이터 재사용, 본인 범위 API 필요 |
| 본인·현장 알림 | 이벤트 ID, 내용, 우선순위, 발생 시각, 상태 | 기존 이벤트 모델 연계 검토 |
| SOS 생성/조회 | 요청 ID, 접수 시각, 관리자 확인, 오류 | 앱용 계약 신규 설계 필요 |
| 알림 읽음 | 작업자별 확인 시각 | 신규 설계 필요 |
| 푸시 등록 | 설치 식별자, 토큰, 작업자 연결 | 신규 설계 필요 |
| 담당자 연락처 | 현장별 연락처와 이름 | 데이터 제공 방식 확정 필요 |

기존 관리자 snapshot을 내려받아 앱에서 본인만 걸러내는 방식으로 권한을 구현하지 않는다. 서버가 모든 조회·수정에서 본인/현장 권한을 검사한다. 모바일 앱에 관리자 공용 비밀번호나 관리자 토큰을 내장하지 않는다.

## 8. UI와 성능 기준

- 주요 버튼 터치 영역은 최소 48dp, SOS는 한눈에 찾을 수 있는 크기로 제공한다.
- 상태는 색과 함께 글자·아이콘을 사용한다. 숫자와 전문용어 대신 행동 안내를 우선한다.
- 데이터 수신 후 화면 반영 목표는 2초 이내다. 안전모 측정 주기·네트워크 지연까지 2초 이내라고 보장하지 않는다.
- SOS는 서버 정상 연결 조건에서 접수 확인 목표 3초, 5초 이상 응답이 없으면 지연 상태와 연락 대안을 표시한다. 제한 시간 뒤 접수 조회로 결과를 확인한다.
- 연결 복구 시 본인 상태와 미확인 알림을 재조회한다. 재접속이 새로운 SOS를 만들지 않는다.
- 배터리 수신 주기 5초 기준, 15초 이상 미수신을 오래된 값으로 표시하는 초안을 적용한다. 서버 온라인 판정과 운영 기준을 맞춘 뒤 확정한다.

## 9. 출시 전 수용 기준

| 시나리오 | 통과 조건 |
| --- | --- |
| 다른 작업자의 ID로 조회 시도 | 서버가 거부하고 정보가 노출되지 않음 |
| 본인 안전모 SOC 수신 | 같은 장치의 값과 수신 시각을 표시 |
| 센서 미수신/오류 | 0%나 정상 상태로 오인시키지 않음 |
| SOS 정상 전송 | 관리자 앱에 같은 사건이 생성되고 서버 접수 후에만 성공 표시 |
| 관리자 확인 | 작업자 앱에도 확인 상태가 반영됨 |
| SOS 요청 재시도 | 중복 사건 없이 기존 신고 결과를 확인 |
| 네트워크 차단 | 전송 실패/상태 확인 불가를 표시하고 전화 대안 제공 |
| 앱 백그라운드 | 실제 Android 기기에서 푸시 수신 확인 |
| 장치 배정 변경/로그아웃 | 이전 사용자 정보와 푸시 연결이 제거됨 |
| 전체 실물 검증 | P4·MAX17048·서버·관리자 앱·작업자 앱을 연결해 수신을 확인 |

## 10. 구현 순서와 미결정 사항

1. 이 PRD의 핵심 범위와 작업자 로그인 방식을 확정한다.
2. 홈·알림·내 안전모·SOS 상태 화면을 시안으로 만든다.
3. 작업자 인증과 본인 범위 API를 만들고, SOS 접수/관리자 확인을 연결한다.
4. Android 푸시와 네트워크 오류 처리를 연결한다.
5. 시뮬레이터에서 검증한 뒤 실제 배선과 P4로 시험한다.

검토가 필요한 결정: Android 우선 여부, 독립 앱 또는 기존 앱의 작업자 모드, 작업자 계정 발급 방식, 담당자 연락처, 작업 시간 외 위치 수집 정책, 데이터 보관 기간. 이 초안의 제안은 구현 완료나 확정된 운영 정책을 뜻하지 않는다.
