# 낙상 의심 안내·응답·관리자 상태 연결

## 개발 배경과 실제 실행 여부

낙상 의심 감지를 보완하기 위해 BNO085 IMU와 함께 UWB 위치 정보와 카메라 영상 활용도 고려했다. 그러나 UWB 위치 정보의 안정성 문제, 영상 기반 낙상 판별을 위한 추가 학습 필요성, 영상 분석·음성 처리 등을 함께 수행할 때의 병목현상이 우려되어 **이번 낙상 판정·응답 확인 과정에서는 UWB와 카메라를 제외했다.** 이는 기존 UWB 위치·카메라 기능을 삭제하거나 비활성화했다는 뜻이 아니다. 낙상 의심 판정은 IMU의 가속도·각속도·자세 변화만 사용한다.

2026-10-17 기준 소스 구현과 대체 데이터를 사용한 시험까지 진행했다. 서버 STT에 필요한 **OpenAI API 키**, 카메라·통화 등 장치 인증 토큰, 실제 서버 주소와 Wi-Fi 등 운영 연결 설정을 전달받지 못해 수정 펌웨어를 실제 P4에 업로드하거나 운영 서버를 실행하여 전체 기능을 직접 확인하지 못했다. OpenAI API 키는 서버의 음성 인식에 사용되며, 펌웨어 적용에는 별도로 실제 장치·네트워크 설정이 필요하다. 따라서 아래 흐름은 구현한 코드의 동작 설계이며, 실제 헬멧에서 정상 동작을 확인했다는 결과가 아니다.

| 조건 | 착용자 안내 | 관리자 메시지 | 표시 상태 |

2026-10-17 사용자 추가 정책: **통화 중 새 낙상 의심 이벤트는 무시한다.** 펌웨어가 통화 중 이벤트를 전송하지 않고, 서버도 `call_active` 또는 연결된 관리자 통화가 있으면 사건을 생성하지 않는다. IMU 원시 기록·로컬 검출 로그는 유지하지만 통화 종료 후 해당 이벤트를 다시 발행하지 않는다. 이미 통화 전에 시작한 사건은 별도 사건으로 유지되며 이후 새 통화가 시작되어 안내가 불가능하면 응답 확인 불가로 처리한다. 통화를 자동 종료하지 않는다.

## 구현 경로

- `main/sensors.c`: 검출 시 대기 없는 큐로 전송 모듈에 전달. IMU 태스크에서 HTTP·STT·스피커를 기다리지 않는다.
- `main/fall_client.c`: 별도 태스크에서 `/api/falls/detect`를 재시도하고 같은 감지 ID를 재사용한다. 서버 사건 ID를 받은 뒤 안내 WAV 준비 상태를 250ms 간격으로 조회하고 기존 버퍼형 스피커 재생 함수를 사용한다.
- `main/voice.c`: 안내 재생 후 별도 낙상 응답 컨텍스트로 VAD 발화를 태깅한다. 낙상 전용 업로드 큐/태스크를 사용해 일반 STT 업로드 대기열과 분리한다. 기존 통화 중 STT 중지, NS/WakeNet 설정, 호출어 처리는 보존한다.
- `main/api_client.c`: 일반 WAV는 기존 `/api/audio/upload`, 태깅된 WAV는 사건 ID가 포함된 `/api/falls/{id}/audio`로 전송한다.
- `routers/falls.py`, `services/fall_service.py`: 기기/작업자 매핑 검증, 감지 중복 방지, 안내 재생 확인, 제한된 STT 처리, 명확한 응답 분류와 상태 변경, 시간 초과 처리.
- 관리자 화면: `fall_incident` WebSocket으로 같은 `event_id`의 행을 교체하고 상태 변경 배너를 표시한다. 최초 감지와 긴급 전환은 각각 `notify=true`로 발행한다. 자동 전화·문자·외부 푸시는 이번 구현 범위가 아니다.

서버는 감지 사건과 관리자 최초 알림을 저장·발행한 다음 TTS 준비를 시작한다. 기기가 새 안내를 재생하고 종료를 확인해야 응답 대기가 열린다. TTS는 기존 `generate_tts()`의 캐시/Edge TTS 경로를 사용하며 네 문구의 새 PCM 파일을 펌웨어에 내장한 것은 아니다. 기존 확인음 PCM은 그대로 유지한다. 따라서 실제 안내에는 정상 서버 연결·TTS 서비스·스피커가 필요하고, API 키 없는 시험에서는 STT/TTS를 대체해 상태 흐름만 검증했다.

## 시간·응답 판정

기기에서 안내 재생 함수가 반환한 시각부터 정확히 8초 동안 새 응답 발화를 받는다. 서버는 재생 완료 보고의 `remaining_ms`로 남은 시간을 설정한다. 재전송으로 창을 다시 열거나 늘리지 않는다. 일반 네트워크 전송 지연만큼 서버와 기기의 마감 시각이 다를 수 있어 실기 종단 측정이 필요하다.

8초 안에 시작한 발화는 최대 5초 녹음을 마칠 수 있다. 기기는 발화 시작을 별도 보고하고, 서버는 한 번만 제한된 녹음/전송/STT 유예를 둔다. 8초 이후 새 발화를 받기 위한 연장이 아니다. 발화 시작 보고가 유실되거나 마감 후 도착하면 시간 초과가 우선될 수 있다. 수신된 음성의 STT는 설정 timeout+2초(최대 15초) 유예를 사용하며 무한 대기하지 않는다. 새 발화가 없는 경우 안내 종료 기준 약 8초 후 긴급 전환한다. 서버 타이머 주기 200ms·전송 지연은 별도다.

전체 문장 일치로 안전 응답은 **`괜찮습니다`**, 구조 요청은 **`도와주세요`**만 받는다. 공백과 지정된 문장부호만 정규화하며 동의어·접두어·다른 표현은 추가로 허용하지 않는다. `네`, 부정문, 안내 문장 반복, 안전/구조 문구가 섞인 문장도 확정하지 않는다. 명확하지 않은 응답은 기록하고 남은 대기시간 동안 재시도를 허용하며 마감 시 응답 확인 불가로 전환한다. 명확한 응답은 STT 결과를 받은 즉시 전환한다. 기존 STT 모델·한국어 설정·명령용 prompt를 재사용하며 일반 호출어의 prompt echo 차단 코드를 변경하지 않았다.

안내 준비/전달 자체가 확인되지 않으면 최초 감지 후 30초의 별도 전달 watchdog으로 응답 확인 불가 긴급 전환한다. 이 값은 8초 응답 대기와 다르다. 안내 생성 실패나 스피커 재생 실패가 확인되면 즉시 같은 긴급 결과로 처리한다. 긴급 상태는 TTS 생성·재생 성공 여부와 무관하게 먼저 저장·통지한다. 결과 TTS도 생성되지 않으면 기기는 실패를 로그로 남기며 관리자 상태는 유지한다.

## 저장·권한·장애 처리

`fall_incidents`, `fall_detections` 두 테이블은 기존 `Base.metadata.create_all()`로 추가된다. 기존 열/데이터를 덮어쓰지 않는다. 운영 DB 적용 전 백업 및 스테이징 확인이 필요하다.
기존 `events`의 단일 사건에 탐지·재생 완료·발화 시작·인식 결과·최종 상태 이력을 JSON으로 누적한다. 감지 ID 재전송 및 활성 사건 중 추가 감지는 별도 알림 사건으로 복제하지 않는다. 의심 해제는 `Event.status=resolved`이지만 이력은 삭제하지 않는다.
관리자 확인/종료 상태와 낙상 상태는 구분한다. 응답 확인 중에는 수동 종료/일괄 종료로 판정을 우회하지 못하게 한다. 긴급 사건은 관리자가 종료할 수 있고, 이때 해당 근로자의 별도 `fall_emergency` 위험만 해제한다. 기존 SOS, 화재, `fallen/man_down` 값을 안전 응답 때문에 지우지 않는다.

새 기기 API는 기존 `CALL_DEVICE_TOKEN`과 동일한 공유 토큰을 Bearer 헤더로 요구한다. 빈 토큰은 거부한다. 등록된 assistant_device와 같은 현장 작업자만 허용하며, 음성은 해당 사건의 장치 ID와 응답 상태를 검증한 후 STT로 보낸다. 관리자 방송도 사건 현장으로 제한한다. 기존 공유 토큰 모델의 한계는 유지되며 기기별 인증 체계를 새로 도입한 것은 아니다.

서버 마감 시각은 DB에 남아 재시작 후에도 시간 초과 처리된다. 기기 전송 큐와 현재 응답 컨텍스트는 RAM에 있어 기기 전원 차단 시 소실된다. 서버에 접수되기 전 오프라인 이벤트는 RAM에서 재시도하며 큐가 가득 차면 로그로 남긴다. 감지 전송이 접수되지 않은 상태만으로 기존 일반 음성 기능을 막지 않는다. 실제 통신 단절에서의 관리자 도착 시간을 보장하지 않는다.

## 검증

응답 문구 통일 후 낙상 상태/API 시험 33개 통과. 기존 음성·호출어·통화 인증·위험 처리 회귀시험 45개와 TypeScript 빌드·Vite 프로덕션 번들 생성은 앞선 연결 구현 검증에서 통과했다. 시험은 가상 DB·STT/TTS 대체를 사용하며 실제 음성 인식률·청취·알림 지연의 검증 결과가 아니다. 새 임계값의 헬멧 현장 검증과 ESP-IDF P4 전체 빌드·실기 업로드는 수행하지 않았다.

### 실제 환경에서 확인·개선할 사항

운영 연결 설정을 확보한 뒤 실제 헬멧과 관리자 화면을 연결하여 다음 사항을 확인해야 한다.

- **낙상 의심 감지:** 현재의 오른쪽 측면 장착 상태에서 낙상에 해당하는 시험 움직임을 감지하는지, 걷기·고개 숙이기·쪼그리기·헬멧 탈착 등 일상 동작을 잘못 감지하지 않는지 확인한다. 사람의 낙상과 벗어 놓은 헬멧의 낙하를 완전히 구분할 수 없는 한계도 유지한다.
- **착용자 안내:** 감지 후 확정한 안내가 실제 스피커에서 누락·깨짐 없이 재생되는지, 재생 종료를 기준으로 8초 응답 대기가 시작되는지 확인한다.
- **관리자 알림:** 초기 알림이 관리자에게 도착하고 동일 사건의 메시지·상태가 갱신되는지, 긴급 전환 때 추가 알림이 전달되는지, 의심 해제 후에도 이력이 남는지 확인한다.
- **음성 인식:** 실제 마이크·주변 소음·여러 착용자의 발음에서 `괜찮습니다`와 `도와주세요`를 정확히 구분하는지, 무응답·인식 실패·그 밖의 표현이 안전 응답으로 잘못 처리되지 않는지 확인한다.

음성 인식을 개선하기 위해 **미리 녹음된 음성파일을 수집·라벨링하고 반복 평가하며, 필요에 따라 이를 음성 인식 모델의 학습·보정에 활용해야 할 수 있다.** 두 확정 문구뿐 아니라 소음·비응답 발화도 함께 비교해 오인식 원인을 확인해야 한다. 구체적인 학습 방식과 대상 모델은 아직 선정하지 않았고, 현재 사용 중인 STT에 추가 학습을 적용하거나 그 효과를 확인한 상태도 아니다. 녹음 음성을 활용한 개선이 실제 낙상 감지나 알림 전달의 검증을 대신하지 않으므로, IMU 감지·스피커 안내·관리자 알림·음성 인식은 각각 확인해야 한다.
