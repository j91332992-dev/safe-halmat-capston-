# P4 카메라 중단 진단 및 카메라 전용 자동복구

2026-10-25 / 브랜치 `integration/hanmir-final-prd-20261016`

## 최종 추가 확인 — 케이블 교체 후 영상 복구

사용자가 FPC 케이블을 교체하고 전원을 다시 켠 뒤 **기존 camretry1 펌웨어 그대로 영상이 복구됐다.** 교체 후 추가 펌웨어 업로드는 하지 않았다. 버스 복구 추가 실험 코드는 장치에 올리지 않았고 정상 camretry1 소스로 정리했다.

- 센서 검출 이후 일시적인 dequeue timeout이 있었으나 자동복구 후 `capturing` 전환. 초기화 2회, 전체 재초기화 1회 성공, 프레임 653→880 증가. `last_error`는 마지막 실패 이력이다.
- 서버 약 **20.11초** 표본: 영상 **11.29FPS**, YOLO **9.95FPS**, 상세 **3.53FPS**. 매 순간 10FPS 이상이나 장시간 통화 동시 부하까지 검증한 것은 아니다.
- 원본 프레임 ID 685→911, 프레임 나이 0/47/15ms. UART 전송 표본은 각 20회 중 실패 0회, 전송 폐기 0개.
- 가용 내부 힙 235,143~239,579바이트, 관측 최소 힙 171,952바이트, PSRAM 30,370,512~30,605,216바이트. UWB 온라인 유지.
- 사용자가 영상 정상 표시를 확인했다. 통화·호출 음질은 이 구간에서 별도로 재시험하지 않았다.
- 케이블 교체·재체결 뒤 회복돼 케이블/접촉 경로 문제가 유력하다. 케이블 내부 결함과 접점 재체결 효과를 분리한 시험은 아니므로 특정 부품 고장으로 확정하지 않는다.
- [복구 후 실제 표본 JSON](evidence/2026-10-25/camera-new-cable-recovered.json).

아래는 **복구 전 진단 이력**이다. 미복구 표시는 당시 상태이며 최종 결과는 이 절을 우선한다.

## 복구 전 결과와 제한

**자동 재시도·오류 기록 펌웨어의 빌드와 COM25 업로드는 완료했다. 영상은 아직 복구되지 않았다.** 기존 정상 펌웨어 원본을 재업로드한 비교 시험, 카메라 FPC 재체결, 완전 전원 차단 후에도 OV5647 센서 ID를 읽지 못한다. 이는 현재 관측한 실패 단계이며 FPC·접점·카메라 전원·센서 중 어느 부품이 원인인지까지 확정한 결과는 아니다.

서버에 남은 마지막 영상은 18:03:06 KST의 과거 프레임이다. 메타데이터의 `received=true`만으로 현재 영상이 들어온다고 판단하면 안 된다. 새로운 frame ID/프레임 나이와 수신 누적값 증가를 함께 확인해야 한다.

## 실제 원본 비교 시험

- 설치된 기존 펌웨어 버전: `2.0.0-p4-cal2-call1-zone1-20261024`.
- `C:/dev/hanmir-p4/helmet_p4/build`에 보존된 마지막 정상 빌드의 앱 바이너리를 그대로 COM25에 재업로드했다. esptool의 플래시 해시 검증 통과.
- 부트로더·NVS·음성 모델·파티션 전체를 지우지 않고 **앱 영역 0x10000만** 썼다.
- 재부팅 로그에서도 동일하게 나타났다:

```text
sccb_i2c: ... failed to transmit receive
ov5647: ov5647_get_sensor_id: read pid_h failed
ov5647: Get sensor ID failed
esp_video_init: Failed to detect camera sensor with address=36
hanmir_p4: camera capture pending board validation: ESP_FAIL
```

주소 `36`은 드라이버가 16진수로 출력하는 센서 주소 `0x36`이다. YOLO/밝기/영상 전송 큐 이전의 센서 제어 통신 단계다. 이번 원본 복원만으로도 영상이 나오지 않았으므로 최근 모바일 UI 수정이 원인이라고 판단할 근거는 없다.

## 수정 내용

### 카메라 작업 소유권과 복구

- 기존에는 부팅 시 초기화 한 번 실패하면 그대로 끝났다. 촬영 중 dequeue/재큐잉 오류로 작업이 종료돼도 촬영 작업을 다시 만들지 않았다. 전송 WebSocket 재연결은 촬영 작업을 살리는 기능과 별개였다.
- 기존과 같은 순서로 최초 초기화하고, 단일 카메라 관리 작업이 촬영 루프와 자원 정리를 맡는다. 같은 장치를 두 작업이 동시에 열거나 콜백에서 자원을 해제하지 않는다.
- 초기화 실패 또는 촬영 루프 종료 뒤 카메라 버퍼·JPEG 엔진·장치 파일을 정리하고 esp_video의 CSI/ISP를 deinit한 뒤 재초기화한다. GPIO·품질·해상도·목표 FPS 설정은 그대로 사용한다.
- 재시도 간격은 5 → 10 → 20 → 최대 30초. 100ms씩 sleep하며 대기해 CPU를 점유하지 않는다. 정리 실패 시 정리부터 다시 수행하며 중복 초기화를 피한다.
- dequeue 오류는 기존 스트림 복구를 먼저 시도하며, 연속 3회 실패하거나 STREAMOFF/재큐잉/STREAMON/QBUF 오류가 나면 카메라 전체 재초기화로 넘어간다. 연속 JPEG 인코딩 오류 3회도 동일하다.
- P4 전체 재부팅, Wi-Fi 재설정, I2S 변경, UWB 태그 수정은 복구 루프에서 하지 않는다. 카메라 SCCB는 기존 I2C0이며 MAX17048의 별도 I2C1 및 BNO UART는 이 자원의 대상이 아니다.
- `restart_camera` 명령도 카메라 소유 작업에 요청만 전달한다. 실시간 콜백에서 드라이버를 직접 종료하지 않는다.

### 오류와 서버 진단

`component_status.camera_diagnostics`에 다음을 추가했다:

- 현재 단계, 마지막 실패 단계, ESP 오류명, errno
- 초기화 횟수, 오류 횟수, 전체 재초기화 성공 횟수, 스트림 재시작 횟수
- 생성한 JPEG 수, 마지막 JPEG 생성 후 경과 ms, 재시도 간격
- 카메라 작업의 최소 잔여 스택

오류 시 UART에는 실패 단계·시도 횟수·내부 힙·최대 연속 블록·PSRAM을 함께 남긴다. 이번 사례에서는 esp_video가 센서 검출 실패를 출력하면서 상위 초기화 함수는 성공을 반환하고, 실제 캡처 장치 파일이 만들어지지 않아 다음 `open()`에서 **errno=2(ENOENT)**가 발생했다. 따라서 추가 진단의 실패 단계는 `device_open`이며, 하위 드라이버의 센서 ID 실패 로그와 함께 해석해야 한다.

`recoveries`는 재초기화 함수의 성공 횟수다. 실제 영상 복구 판정에는 `frames` 증가와 서버 새 영상 수신도 필요하다.

### 변경 파일

- `firmware/helmet_p4/main/camera_source.c`: 촬영 루프/복구/진단.
- `firmware/helmet_p4/main/hanmir.h`: 카메라 진단/재시작 선언.
- `firmware/helmet_p4/main/api_client.c`: 진단 heartbeat와 새 펌웨어 버전.
- `firmware/helmet_p4/main/command_client.c`: 카메라만 재시작하는 명령 수신.
- `backend/app/schemas/api.py`: 기존 관리자 장치 명령 API에 `restart_camera` 유형 허용.

**현재 서버는 재시작하지 않았다.** 자동복구와 heartbeat 진단은 장치에서 실제 동작한다. REST를 통한 수동 `restart_camera`는 변경한 서버 소스를 다음에 재시작하여 반영해야 한다. 이번에는 카메라 무응답 상태에서 자동 실패/재시도 경로를 검증했으며 수동 REST 명령의 실기기 복구 성공은 확인하지 않았다.

재시도 중의 P4·UWB·마이크/스피커 초기화·방향 수신은 확인했다. 부팅 직후 네트워크 준비 전의 일시적 Host unreachable과 준비 후의 센서 무응답은 구분했다. 이 짧은 시험은 장시간 메모리 누수 부재나 양방향 통화 음질 유지까지 증명하지 않는다. 실제 음성 호출/청취와 통화는 이번 구간에서 다시 시험하지 않았다.

FPC 재체결 후에도 센서 무응답이 이어졌다. 이후 PC USB·충전 USB·배터리 전원을 차단하고 다시 켰을 때 재시도 횟수가 새로 시작한 것으로 완전 재부팅을 확인했지만 카메라는 여전히 unavailable/0프레임이다. 이때도 P4·UWB는 온라인이다. 후속 표본은 위 JSON의 `after_complete_power_cycle`에 기록한다.

## 다음 확인

반복 재부팅이나 YOLO 임계값 변경을 계속하지 않는다. 다음은 양쪽 FPC 방향/잠금·접점 확인과 FPC/OV5647 모듈 교차 시험이다. 연결 확인은 반드시 모든 전원을 끈 뒤 수행한다. 소프트웨어 재시도로 응답 없는 센서가 반드시 살아난다고 보장하지 않는다.

센서가 응답하면 새 프레임 수/프레임 나이 → 60초 수신·YOLO·상세 FPS → 실제 호출/TTS → 양방향 통화를 순서대로 확인한다. 그 뒤 카메라만 재시작하는 명령으로 복구 성공 경로와 메모리 회수도 검증해야 한다. **현재는 영상 복구 및 10FPS 유지 확인을 완료 처리하지 않는다.**

실제 Wi-Fi 자격 증명이 들어 있는 sdkconfig·펌웨어 바이너리·원시 서버 로그는 공개 저장소에 추가하지 않고 로컬 진단 폴더에 보관했다.
