# 한미르 스마트 안전모 프로젝트: 현재 상태 및 향후 계획

> 최종 갱신: 2026-08-12  
> 기준 브랜치: `main`  
> 최신 기능 커밋: `1cacf5d feat: stabilize vision pipeline and document PC setup`

## 1. 프로젝트 목표

작업자가 착용하는 ESP32-S3 기반 안전모와 UWB 태그, 관리자 웹을 연결해 다음을 제공하는 현장 안전관리 시스템이다.

- **음성 AI:** `투투스` 호출 후 작업자의 지시를 인식하고, 짧은 음성으로 응답한다.
- **관리자 통화:** 안전모에서 관리자 연결을 요청하고, 관리자 웹에서 통화를 수락·종료한다.
- **영상 안전 감지:** ESP32-S3 카메라 영상으로 사람·보호구·화재·연기를 YOLO로 감지한다.
- **UWB 위치:** 4개 앵커와 태그 거리값으로 안전모 위치를 지도에 표시한다.
- **관리자 웹:** 장치 상태, 위치, 위험 이벤트, 카메라 분석, 통화, 하드웨어 진단을 한 화면에서 관리한다.

## 2. 현재 전체 구성

```text
안전모(ESP32-S3)
 ├─ OV5640 카메라 → JPEG/HTTP → FastAPI 서버 → YOLO → 관리자 웹
 ├─ INMP441 마이크 → VAD/WAV/HTTP → STT·명령 처리·TTS
 ├─ MAX98357A 스피커 ← TTS·안내음·통화 음성
 └─ WebSocket ↔ 관리자 통화·장치 명령

UWB 태그(DW3000) → USB COM → UWB 브리지 → FastAPI 서버 → 지도 웹 화면

관리자 웹(React/Vite) ↔ FastAPI/WebSocket ↔ SQLite·YOLO·음성 서비스
```

주요 폴더:

| 위치 | 역할 |
|---|---|
| `firmware/helmet_av_device` | ESP32-S3 안전모: 카메라, 마이크, 스피커, 통화, 장치 명령 |
| `firmware/uwb_position_device` | UWB 태그 펌웨어 |
| `firmware/uwb_anchor` | UWB 앵커 펌웨어 |
| `backend` | FastAPI 서버, SQLite, YOLO, 음성·통화·위치 서비스 |
| `frontend` | React/Vite 관리자 웹 |
| `docs` | 하드웨어, 소프트웨어, 인수인계 문서 |

## 3. 완료된 기능

### 3.1 음성 AI와 명령 처리

- `투투스` 호출어를 감지한 뒤 `네, 말씀하세요`로 응답한다.
- 호출 이후 후속 명령을 일정 시간 듣고, 말이 없거나 이해하지 못한 경우 재질문은 **한 번만** 한다.
- 위치 확인, 관리자 연결, 비상 상황 등 정해진 명령은 복잡한 AI 응답보다 먼저 처리하도록 구성했다.
- 일반 AI 응답은 핵심만 짧게 말하도록 출력 토큰을 제한했다.
- 안전모가 말하는 중에도 `그만`, `그만 말해`, `조용히` 등의 명령으로 음성을 중단할 수 있다.
- 마이크를 스피커 출력 때문에 강제로 계속 차단하지 않으며, 짧은 재개 대기만 둔다.

### 3.2 관리자 통화

- 안전모에서 관리자 연결 요청 가능.
- 안전모 발신 시 연결 대기 중 컬러링 재생.
- 관리자가 수락하면 연결음 1회, 종료 시 종료음 재생.
- 관리자가 30초 안에 수락하지 않으면 안전모가 상대가 받지 않았음을 알리고 종료한다.
- 통화 중 `끊어줘`, `통화 종료`, `중단` 등 음성 명령으로 작업자가 종료할 수 있다.
- 관리자 웹에서 통화 수락·종료와 통화음을 제공한다.

### 3.3 카메라·YOLO

- ESP32-S3 카메라가 VGA `640×480` JPEG를 서버로 보낸다.
- 서버는 프레임을 수신한 뒤 즉시 `202 Accepted`를 반환한다.
- YOLO는 별도 프로세스와 크기 1의 최신 프레임 큐에서 실행한다. 오래된 프레임을 쌓지 않고 새 프레임으로 교체해 지연이 누적되지 않게 한다.
- 분석 결과는 메모리 캐시에서 관리자 웹으로 제공한다.
- 화재는 confidence `0.75` 이상이면서 연속 3프레임 확인 시에만 사고로 처리한다.
- 현재 모델은 `best.pt`이며 약 **6.0MB**, **3,014,358 파라미터**, YOLOv8n급 경량 검출 모델이다.

### 3.4 UWB 위치

- 앵커 4개 기준 위치 계산 구조를 적용했다.
- `a002` 앵커가 간헐적으로 안 뜨는 현상은 장치/수신 상태에서 확인할 수 있도록 했다.
- 미세한 오차로 지도 아이콘이 흔들리는 문제를 줄이기 위해 EMA, 정지 반경, 이동 시작 거리, 연속 샘플 확인 방식을 적용했다.
- 의미 있는 이동만 지도에 반영하도록 30cm 이동 및 연속 확인 기준을 사용한다.

### 3.5 관리자 웹과 진단

- 장치 heartbeat와 실제 수신 기록을 바탕으로 카메라·마이크·스피커 상태를 표시한다.
- 배터리 잔량을 실제로 측정할 수 없는 부품은 임의 값 대신 미지원 상태로 표시한다.
- 미처리 경보를 한곳에서 확인할 수 있다.
- 화재 경보 시 관련 카메라 영상을 팝업에서 함께 확인할 수 있다.
- 카메라 분석 화면, 작업자 상세, 화재 대피 모달의 표시 주기와 상태 갱신을 보완했다.

## 5. 최근 카메라 성능 측정 결과

ESP32-S3와 현재 서버 노트북에서 실제로 측정한 값이다. 측정 환경과 화면 장면에 따라 조금 달라질 수 있다.

| 항목 | 실제 측정값 | 의미 |
|---|---:|---|
| ESP → 서버 수신 | 약 5.27 FPS | 목표 6 FPS에 거의 도달 |
| JPEG 평균 크기 | 약 16.77KB | 전송 파일 크기 안정적 |
| 카메라 데이터량 | 약 0.724Mbps | Wi-Fi 대역폭 자체는 부족하지 않음 |
| Wi-Fi RSSI | -58dBm | 양호 |
| YOLO 분석 완료 | 약 2.40 FPS | 목표 3 FPS보다 낮음 |
| 15초간 큐에서 폐기된 프레임 | 29장 | 최신 화면 유지를 위한 의도적 교체 |
| YOLO 처리시간 | 약 72.8~1,084.1ms | CPU 부하에 따라 큰 변동 |
| 노트북 전체 CPU | 평균 76.5%, 최대 100% | 주요 병목 |

### 핵심 결론

1. **ESP32가 영상을 못 보내는 문제가 주원인은 아니다.** 실제 서버 수신은 약 5.27 FPS, Wi-Fi 신호도 양호하다.
2. **웹의 분석 화면이 끊기는 주원인은 서버 YOLO 처리량이다.** 수신은 5 FPS 이상이지만 분석 완료는 약 2.4 FPS다.
3. 웹 화면이 6 FPS로 새로고침돼도 새 YOLO 결과가 약 2.4 FPS뿐이라 같은 분석 이미지가 반복 표시될 수 있다.
4. 음성 인식과 카메라는 상당 부분 분리돼 있지만, 같은 Wi-Fi와 같은 노트북 CPU를 공유하므로 동시 작업 시 지연 변동이 생길 수 있다.

## 6. 현재 해결 중인 가장 큰 과제: PPE 인식 품질과 YOLO 속도

### 6.1 문제 상황

노트북 웹캠으로 `best.pt`를 실행할 때는 장갑·조끼가 비교적 잘 인식됐지만, ESP32-S3 카메라 영상을 서버로 받아 분석할 때는 장갑·조끼가 잘 안 잡히는 현상이 있다.

주요 원인 후보:

- ESP 카메라의 렌즈·초점·노출·시야각이 노트북 웹캠과 다름
- ESP 원본 `640×480`을 YOLO 입력 `320`으로 축소하면서 작은 장갑 픽셀이 크게 줄어듦
- 현재 모델이 장갑과 조끼를 여러 유사 클래스로 나눠 학습함
- CPU 부하에 따라 YOLO 처리시간이 흔들리고 프레임이 교체됨

실제 같은 ESP 이미지에서 장갑 confidence는 다음처럼 달라졌다.

| YOLO 입력 크기 | 장갑 confidence 예시 |
|---|---:|
| 320 | 0.156 |
| 640 | 0.534 |

이는 작은 보호구가 축소 입력에서 손실되는 경향을 보여준다.

### 6.2 현재의 PPE 확대 분석

현재 서버는 사람이 검출된 경우에 한해, 약 1초 간격으로 사람 영역을 잘라 YOLO를 한 번 더 실행하는 보조 분석을 넣어 두었다.

```text
ESP 원본 640×480
        ↓
전체 화면 YOLO 320: 사람·화재·연기 우선 확인
        ↓
사람이 잡힌 경우만 사람 영역 crop
        ↓
PPE 보조 YOLO 320: 장갑·조끼·헬멧을 더 크게 확인
```

장점은 장갑·조끼가 모델 입력에서 커진다는 점이다. 단점은 일부 프레임에서 YOLO를 두 번 실행하므로 처리시간이 늘어난다는 점이다. 이 기능은 **임시 보완책**이며, 최종 해법으로 무조건 유지할 필요는 없다.

### 6.3 권장 최종 해법

1. 실제 ESP32 카메라로 찍은 사진을 충분히 확보한다.
2. Roboflow에서 라벨을 아래 6개로 통합한다.

```text
person
helmet
glove
vest
fire
smoke
```

3. Colab에서 `imgsz=640` 기준으로 새 YOLO 모델을 학습한다.
4. 새 모델을 서버 전체 화면 `416`부터 시험한다.
5. 전체 416만으로 장갑·조끼가 충분하면 사람 crop 재분석을 끄거나 빈도를 낮춘다.
6. 부족할 때만 사람 영역 확대 분석을 640으로 사용한다.
7. 서버 PC CPU/GPU를 개선하면 전체 분석 FPS와 음성·YOLO 동시 실행 안정성이 좋아진다.

### 6.4 데이터셋 준비 원칙

- Roboflow API 키는 노트북 파일이나 GitHub에 넣지 않는다.
- API 키는 Colab Secret 또는 `getpass()`로 입력한다.
- 사진 수는 1,000장 이상을 목표로 하되, 비슷한 사진만 많이 넣는 것보다 다양성이 중요하다.
- 실제 ESP32 카메라 프레임을 학습 데이터의 최소 30~50% 포함한다.
- 장갑·조끼의 거리, 색, 조명, 각도, 가림, 미착용 상태를 모두 포함한다.
- 불과 비슷한 노란 조명, 빨간 물체, 반사광도 음성 예제로 넣어 오탐을 줄인다.

## 7. 현재 `best.pt`의 개선 필요점

현재 `best.pt`는 18개 클래스를 갖고 있으며, 서비스에서 필요하지 않은 `body`, `head`, `hand`, `foot`, `pants`, `light`, `no-fire` 등이 섞여 있다. 또한 장갑과 조끼가 여러 표기로 나뉘어 있다.

```text
장갑: safetyglove, safeyglove, gloves
조끼: safetyvest, vest
```

서버는 이를 하나로 합쳐 처리하지만, 모델은 서로 다른 클래스로 confidence를 분산해 학습한다. 새 학습에서는 불필요한 클래스를 제거하고 장갑·조끼를 각각 하나의 클래스로 통합해야 한다.

## 8. 다른 PC에서 실행하는 방법

상세 절차는 루트의 `다른_PC_설치_및_실행_가이드.md`를 따른다.

간단 순서:

```bat
git clone https://github.com/j91332992-dev/safe-halmat-capston-.git
cd safe-halmat-capston-
install_windows.bat
install_ai_windows.bat
copy backend\.env.example backend\.env
.\.venv\Scripts\python.exe configure_av_device.py
```

이후 ESP32-S3를 USB로 연결하고 실제 COM 번호를 넣어 업로드한다.

```bat
cd firmware\helmet_av_device
..\..\.venv\Scripts\python.exe -m platformio run --target upload --upload-port COM13
cd ..\..
run_integrated_hardware.bat
```

UWB 태그가 별도 USB COM 포트라면:

```bat
run_hardware_map.bat COM18
```

로컬 환경마다 다시 만들어야 하며 GitHub에 올리면 안 되는 파일:

- `backend/.env`
- `firmware/helmet_av_device/include/device_secrets.h`
- `.venv`, `node_modules`, `.pio`
- DB, 카메라 캡처, 음성, TTS 출력 파일

## 11. 판단 기준

다음 조건을 만족하면 PPE 확대 분석을 줄이거나 제거할 수 있다.

- ESP 테스트 이미지에서 장갑·조끼 recall이 충분히 높음
- 전체 화면 416 분석만으로 장갑·조끼 confidence가 기준값 이상
