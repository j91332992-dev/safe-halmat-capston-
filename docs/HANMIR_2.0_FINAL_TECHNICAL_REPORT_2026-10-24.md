## 0. 이 문서부터 읽기

HANMIR은 기존 ESP32-S3 안전모를 DFR1172 ESP32-P4 + 내장 ESP32-C6 구조로 이식하고, 카메라·음성·위치·방향·안전 알림·통화를 통합한 캡스톤 프로젝트다. 현재 단계의 목표는 기능 추가를 계속하는 것이 아니라, 실제로 확인한 버전을 보존하고 시연을 완성하는 것이다.

이 문서는 구현한 것, 실제로 시험한 것, 사용자 청취 확인, 아직 확인하지 못한 것을 구분한다. **평균 10FPS ≠ 매 순간 10FPS, 검출 신뢰도 ≠ 정확도, 지도 아이콘 고정 ≠ 실제 위치 오차 0m, 전송 성공 ≠ 사람이 들음**이다.

## 2. 최종 시스템 구조

```text
OV5647 ── MIPI CSI ─┐
INMP441 ── I2S RX ──┤
BNO085 ── UART ─────┤ ESP32-P4 ── SDIO ── 내장 C6 ── 2.4GHz AP
MAX17048 ─ I2C1 ────┤     │                              │
MAX98357A ← I2S TX ──┘     └─ 명령/TTS/통화 재생             │
                                                        ▼
독립 ESP32+DW3000 태그 ← UWB → 앵커 1~4       FastAPI / SQLite / GPU 추론
            └──────── 독립 Wi-Fi ──────────────┤
                                             └─ React 웹 / Capacitor 앱
```

P4가 모든 AI를 직접 실행하는 구조가 아니다. P4는 영상 입력·JPEG·마이크 처리·오디오 재생·센서·로컬 낙상 후보를 맡고, PC가 YOLO·위치 계산·안전 규칙·STT/LLM 연결을 맡는다. UWB 태그는 P4와 데이터선을 공유하지 않는 별도 장치다. ESP32-C5/ESP-NOW 영상 중계는 최종 채택하지 않았다.

### 통신 경로

| 데이터 | 경로 | 정체를 제한하는 방식 |
|---|---|---|
| 영상 | `/api/camera/stream/{device_id}`, HMR2+JPEG WebSocket | 최신 1장 큐, 인코딩 전 큐 확인, 오래된 프레임 교체 |
| 음성 명령 | `/api/audio/upload` | 발화 구간 WAV, 제한 큐, 지원 시 무손실 압축 |
| 명령·방향 | `/ws/device/{device_id}` | 방향 100ms 전송, 짧은 송신 대기, 최신값 사용 |
| 실시간 통화 | `/ws/call/device/...`, `/ws/call/operator/...` | 소켓별 writer, 용량/나이 제한, 재버퍼링 |
| UWB | `/api/uwb/stream`, HTTP 호환 경로 유지 | RF 루프와 네트워크 분리, 순서·시간·품질 검사 |
| 화면 갱신 | `/ws/dashboard` | 화면별 writer, 위치·방향·heartbeat 병합, 느린 화면 분리 |

HTTP/WS 기반 현장 LAN 데모다. WAN/TLS·장치별 인증·운영 보안 전체가 완성된 배포 시스템으로 주장하지 않는다. 두 AP 정보 저장과 서버 자동 검색은 다른 기능이다. **서버 IP 자동 검색은 없다.**

## 3. 하드웨어·배선 기준

DFR1172 실제 칩 rev 1.3, 물리 Flash 16MiB, PSRAM 32MiB를 확인했다. `VCC`는 외부 5V, `3V3`는 센서 3.3V 계통이다. 핀번호와 단위시험 성공을 다른 보드 리비전에 그대로 일반화하지 않는다.

| 부품 | 현재 프로젝트 배선/역할 |
|---|---|
| OV5647 | **CSI** FPC. DSI가 아님. SCCB SDA7/SCL8, 주소 0x36 |
| INMP441 | VDD3.3V, GND, SCK31/WS34/SD36, L/R→GND(좌 슬롯) |
| MAX98357A | VIN 스위치 후 5V, 공통 GND, BCLK20/LRC21/DIN22 |
| 8Ω 스피커 | MAX SPK+ / SPK−. SPK−는 공통 GND와 다름 |
| MAX17048 | 논리 VIN3.3V, SDA33/SCL32, I2C1 0x36, 배터리 측 JST |
| BNO085 | 센서 TX(SDA표기)→P4 RX23, 센서 RX(SCL표기)→P4 TX51. P1 HIGH/P0 LOW 표준 UART |
| 내장 C6 | SDIO14~19, RESET54. 제조사 연결 사용 |
| UWB 태그 | 전원만 공유, P4 GPIO 데이터선 없음 |
| microSD | 보드 내장 GPIO39~45 예약. 전체 저장 기능 실사용 검증과 별개 |

카메라와 MAX17048은 주소가 같지만 **서로 다른 I2C 버스**다. GPIO 중복 및 비활성 핀은 `pin_guard.c`로 관리한다. [배선 그림](HANMIR_P4_WIRING_REFERENCE_2026-10-23.png)도 참고한다.

과거 USB 소실·무전원·스피커 무음 문제가 있었다. 롤백·케이블/전원·PCM/I2S·독립 GPIO를 비교했고 이후 실제 출력은 복구됐다. 그러나 모든 무전원 이력을 ‘RESET 때문에 고장’ 또는 특정 보호회로 동작으로 확정할 근거는 없다. 접지/전원 관련 관찰과 소프트웨어 재생 성공을 구분한다. 현재 정상 배선을 다시 바꾸기 위한 문서가 아니다.

## 4. 카메라·YOLO 속도와 화질 개선

### 4.1 처음 느렸던 이유와 변경

전송률뿐 아니라 전체 영상·상세 ROI 추론의 직렬 대기, CPU 추론, 화면 재조회, 이벤트 루프의 동기 DB/파일 처리 등이 겹쳤다. 낮은 해상도로만 줄이면 장갑·안전모가 더 작아져 검출이 떨어졌으므로 단순 축소안을 최종 해법으로 채택하지 않았다.

1. 전체 640 fast lane과 상세 PPE 처리를 별도 프로세스로 분리.
2. 사람·머리·몸통·손 ROI 확대 및 상세 960 경로 사용.
3. Intel Arc iGPU/OpenVINO 활용, PyTorch/OpenVINO 대체 경로 유지.
4. 음성 처리 중 YOLO를 1FPS로 강제 제한하던 경로 제거.
5. 서버에 일반 JPEG를 매번 파일로 저장하지 않고 메모리 처리. 알림 근거 이미지는 별도로 보존.
6. 미리보기는 구독자가 필요할 때 만들고 같은 프레임 재사용.
7. 상세 화면은 새 frame_id만 받도록 하고 겹치는 요청을 방지. metadata 한 표본 5,016→106바이트로 경량화.
8. P4 촬영 마감시간을 마이크로초 기준으로 계산하고, 전송 큐가 막히면 새 JPEG 압축을 생략.

### 4.2 성능 기록

| 단계·조건 | 수신 FPS | YOLO 완료 FPS | 상세 FPS |
|---|---:|---:|---:|
| 10/9 초기 15FPS/640 시험 | 2.57 | 1.98 | 별도 미집계 |
| 10/16 직렬 분석 46.42초 | 10.49 | 2.13 | 별도 미집계 |
| GPU960·조끼·화면 경량화 56.13초 | 14.66 | 11.17 | 3.58 |
| 10/17 약 197.16초 통화 | 16.053 | 11.087 | 3.657 |
| 10/24 30분 시험의 통화 10분 | 14.85 | 6.64 | 2.64 |
| 10/24 최종 구역 경고 기록 74.09초 | 11.85 | **10.20** | **3.55** |
| 위 기록 중 시험 통화 표본 구간 32.70초 | 11.19 | **9.97** | **3.61** |

초기 1.98과 최근 10.20의 숫자상 차이는 약 5.15배다. **장면·버전·구간·동시 기능이 다른 이력 비교**이며 동일 조건 A/B의 확정 개선율은 아니다. 30분 기록의 성능 저하도 보존하며 가장 좋은 한 구간만 대표값으로 쓰지 않는다.

같은 8장 비교에서는 PyTorch 추론 중앙값 **109.59→25.02ms**, 약 77.2% 감소였다. 이는 해당 파일·PC의 비교다. 다른 PC에서 GPU 모델을 준비하지 않고 CPU로 실행하면 같은 FPS가 나오지 않을 수 있다.

### 4.3 밝기·색감·상자

- 분석 gamma **1.35**, 표시 gamma **1.75**, red gain **1.08**, blue gain **0.96**, sharpen **0.2** 유지.
- 센서 수동 노출값이 아니라 서버 분석·미리보기 보정이다. 표시만 밝아진 것과 모델 입력 변화는 구분한다.
- 사람·안전모·조끼·장갑 박스는 서로 다른 색으로 표시한다. FPS·ms·결과 나이도 구분한다.
- 전체 YOLO가 10~11FPS라도 상세 PPE가 약 3~4FPS면 상세 박스가 새로 계산되는 주기도 그에 따른다. 옛 박스를 새 영상에 붙인 것을 새 추론으로 세지 않는다.

## 5. 보호구 검출과 관리자 알림

### 검출 개선 수치

| 비교 | 결과 | 해석 |
|---|---|---|
| 초기 안전모 ROI 개선 | 착용 8장 0/8→3/8 | 개선 초기 단계. 최종 성능이 아님 |
| 조끼 임계값 .40/.35/.30/.25 | 같은 착용 20장 6/9/15/19장 검출 | .25 채택. .40 대비 +13장, 검출 비율 +65%p |
| 조끼 미착용 비교 | 19장 중 오탐 0장 | 그 옷·장면의 결과, 모든 평상복 일반화 아님 |
| 새 연속 상세 20개 | 안전모20/20, 조끼19/20, 장갑20/20, 동시19/20 | 당시 18/20 요구 충족 |
| 맨손 비교 | 장갑 오탐 11/16 | 여전히 중요한 제한. 착용 검출률과 별도로 공개 |

당시 양성 점수 범위: 안전모 .456~.726, 조끼 .250~.616, 장갑 .666~.839. 장갑은 색상 보조 규칙도 사용하므로 모든 점수를 순수 glove 모델의 확률로 부르면 안 된다. 신뢰도를 낮췄다고 실제 정확도가 자동으로 올라간 것도 아니다.

### 현재 관리자 알림 로직

화면 전체에서 남의 장갑을 합산하거나, 손이 안 보인다는 이유로 미착용 확정하던 방향을 바꾸었다.

1. 카메라별 임시 사람 ID, IoU≥0.35의 유일 대응에서만 이력 유지.
2. 겹침·부위 미검출·작음·잘림·흐림은 **확인 불가**. 없는 부위를 추정해서 결론내지 않는다.
3. 최근 **2초**, 유효 관측 **6회 이상**, 관측 폭 **1.5초 이상**, 미검출 **80% 이상**이면 미착용 의심/장갑 확인 필요.
4. 최초 알림 1회, 같은 상태가 15초 이상 지속되고 조건을 다시 채우면 재알림 1회. 이후 같은 사건 유지.
5. 긍정 결과가 연속 3회·1초 이상이면 착용 복구. 사람이 사라진 것은 ‘착용 완료’와 구분.
6. **관리자용 PPE_OBSERVATION 이벤트다. 이 기능은 안전모에 PPE TTS를 보내지 않는다.**

추가 모델 없이 기존 상세 부위 후보와 작은 ROI 품질 검사를 사용한다. 추적 ID는 실명/얼굴 식별이 아니다. 해당 새 정책의 다인 교차·가림·여러 옷 현장 검증은 별도다. 자세한 기준은 [PPE 관리자 정책](HANMIR_PPE_ADMIN_POLICY_2026-10-24.md).

## 6. 음성 입력·투투스·AI 에이전트

### 6.1 실제 운영 경로와 모델

```text
마이크 → P4 I2S/AFE VAD·프리롤 → WAV(필요 시 무손실 압축)
 → 서버 STT → 호출어/후속 발화/비상 분류
 → DB·규칙·지도 계산 또는 설명형 LLM
 → 화면 응답 + 짧은 TTS/내장 안내 PCM → 안전모 스피커
```

| 항목 | 코드·로컬 설정 기준 |
|---|---|
| STT | `gpt-4o-mini-transcribe`, 한국어, 제한 10초, SDK 자동 retry 0 |
| 설명형 모델 | `gpt-6-luna`, 제한 5초, 출력 80토큰, 해당 모델 reasoning none 요청 |
| TTS | Edge TTS `ko-KR-SunHiNeural`, 16kHz/16bit/mono WAV 캐시 |
| 호출 후속 허용 | 20초 |
| 조회 | battery/location/PPE/device/risk 등은 규칙·DB 우선, 불필요한 설명 LLM 미호출 |
| 방향·대피 계산 | 코드가 수행. LLM이 지도 밖 방향이나 새 경로를 창작하지 않음 |
| 답변 | 짧은 한국어, 숫자 먼저, 빈 정보는 확인 불가. 설명형 후처리 최대 120문자 |

실제 계정 청구내역을 조회하지 않았으므로 프로젝트 전체 API비용은 이번 보고서에서 산출하지 않았다. 단순조회·지도계산에서 설명형 LLM 호출을 생략하고, TTS캐시·STT동시성/타임아웃으로 비용·대기를 제한한다. STT는 조회형 질문에도 필요할 수 있다.

계획에 있던 `get_worker_status()` 등은 도구 역할을 설명한 이름이다. 현재 코드의 intent·조회·계산 서비스와, LLM이 임의로 여러 function call을 수행하는 에이전트 런타임을 동일시하지 않는다.

### 6.2 인식·지연 개선과 실제 한계

- 처음 60~70%라는 숫자는 사용자의 기억상 추정치였고 통제 측정 성공률은 아니다.
- 원시 PCM·좌우 슬롯·RMS·0값 비율·WAV·STT 원문을 단계별로 기록해 마이크와 호출 판정을 분리했다.
- 최종 안정 경로는 외부 NS OFF. AEC는 실제 스피커 reference가 없어 완성되지 않았다. ‘노이즈 제거 모델을 켰으니 정확도가 올랐다’고 기록하지 않는다.
- 프리롤300ms, AFE 무음192ms+추가160ms, 내장 ACK PCM46,896B, 앞 무음 약180ms 제거.
- 안내 ‘네, 말씀하세요’는 내장 PCM으로 빠르게 재생하지만 **투투스 판정 자체는 현재 서버 STT 의존**이다.
- STT 힌트를 뺀 뒤 사용자는 5회 중 1회 응답을 보고했다. 같은 원본 4개가 Tu/Kršc/Totus/주스 등으로 전사된 것을 확인하고 힌트를 복구하자 같은 원본 4개가 투투스로 전사됐다.
- 후속 실제 호출 3건의 STT는 834.7/873.6/1,100.4ms, 배터리 질문 716.2ms. 서버 전체는 891.8/926.2/1,147.8/769.7ms였다. 사용자는 정상 청취를 확인했다.
- 이 값은 발화 끝→첫 소리의 종단 측정이 아니다. **최대 0.5초 로컬 호출 목표는 미달/미검증**이다.

### 6.3 로컬 웨이크 모델 연구는 어디까지 했나

69개 첫 수집의 사람 라벨: 양성9/음성60. 두 번째 최종38개: 양성9/음성28/제외1. 합계 양성18/음성88로 pilot 학습을 진행했다. 같은 화자의 작은 자료이며 독립 화자 검증이 아니다.

MixedNet 5,601파라미터, int8 streaming TFLite **29,336B**, microfrontend40채널/10ms step을 준비했다. v2에서 threshold .5는 비호출도 모두 검출했고, .7은 validation2/3·test3/3이었다. 연속 상태 평가는 합성 호출2/3·비호출0/9로 독립 파일 초기화 결과와 달랐다. P4 shadow851추론에서 최대11.917ms, 큐 대기13.666ms, drop0을 기록했으나 실제 호출 응답을 실행하는 검증은 아니었다.

따라서 운영 WakeNet/로컬 shadow는 **OFF**다. 학습해 뒀다는 사실과 검증된 로컬 호출 모델을 제품에 설치했다는 주장을 구분한다. 비상어 로컬 인식도 없어 일반 WAV 전송을 전부 없애지 않았다.

### 6.4 TTS·무손실 전송

TTS403, 톤 fallback, I2S 전체 쓰기, 실제 청취를 구분했고 WAV를 먼저 받아 버퍼 재생하도록 개선했다. 사용자는 이후 호출·배터리 응답 속도와 음질이 정상이라고 확인했다.

51개 명령 파일에서 **2,015,556→1,546,896B, 23.25%** 파일 본문 감소를 기록했다. 같은 WAV로 무손실 복원한 뒤 STT에 넣는다. 압축 시간15.587~66.604ms가 추가되므로 소비전력 절감률로 바꾸면 안 된다.

첫 압축 후보는 6KiB 업로드 스택 부족으로 Stack protection fault가 발생해 기존 WAV로 복구했다. 스택을 **16KiB**로 늘리고 정상 확인 후 다시 무손실 전송을 켰다. 실패 후보를 현재 정상 설정으로 다시 설치하지 않는다.

## 7. UWB 위치·정지 안정화·이동·지도

### 7.1 통신 주기와 표시 추종

| 단계 | 서버 수신 빈도 | 간격 중앙값 |
|---|---:|---:|
| 100ms RF + 기존 HTTP | 3.87Hz | 173ms |
| TCP 재사용·compact ACK | 5.56Hz | 127ms |
| 첫 WebSocket 60초 | 8.85Hz | 80.7ms |
| 후속 실제 이동 157.96초 | 9.07Hz | P95 340ms, 최대1.421초 |

동일 조건만의 비교는 아니다. RF100ms와 서버100ms는 다른 지표다. 반복 HTTP 접속·응답·큐 대기를 줄이고 지속 연결을 사용했다. 2~4번은 poll 응답자이므로 주기만 바꿀 때 반드시 전부 다시 업로드할 필요는 없지만, DS-TWR 프로토콜 변경 때는 네 앵커를 모두 업데이트했다.

### 7.2 좌표 튐 억제

- 거리 median5, 기존 30cm 이동 시작·방향 일관성, 정지 반경15cm·EMA0.35를 유지.
- 정지 판단을 표본 개수만으로 하지 않고 최근0.8초의 범위/전후 위치로 판단. 0.5초 초과 공백은 정지 증거 초기화.
- 웹은 100ms 선형 보간, 외삽 없음. 화면 보간 좌표를 위험 판단용 실제 좌표로 되먹이지 않는다.
- quality weighted: 정상1.0/의심0.35/강한 반사 의심0.15/진단 없음0.20. 기존 client quality보다 높이지 않고 회복은 관측당0.10씩.
- 순간 점프 허용 반경 `min(0.60m, 3m/s×dt+0.20m)`. 벗어나면 보류, 최소3개·0.30초의 연속 후보를 재확인.
- 앵커 부족·held·만료·비유한값·중복·역순은 따로 사유 기록. 튄 좌표를 바로 평활화·위험구역 판단에 넣지 않는다.

같은739후보 오프라인 재생에서 표시 갱신170→372회, 최대 단계46→35.8cm였다. 실제 이동은 멈춤 오판과 화면 끊김이 줄었다고 사용자가 확인했다. 합성 1개 앵커 +0.8m 편향 예시는 가중치 조정 후 오차0.4039→0.1042m였지만 실제 공장 정확도 개선율은 아니다.

저장 설계5.2×3.5, 앵커Y3.6, 지도 밖 출구·시험 위험구역 때문에 apply API가409를 반환해 기존5.6×3.7이 남았던 문제였다. 실패를 무시하고 적용된 것으로 표시하지 않게 상단 오류/객체 선택·범위 검사를 추가했다. 사용자 확인 후 시험 구역을 지우고 **5.2×3.6m**로 적용, layout/draft/dashboard의 동일 치수를 확인했다.

### 7.5 10초 앵커 측량·DS-TWR

### 7.6 `future_frame` 좌표 정지 원인과 수정

마지막 구역 시험 전에는 앵커 네 거리값이 있어도 오래된 uptime→UTC 기준점 때문에 후속 프레임이 미래로 분류돼 거부됐다(한 구간364회). 태그 시계 드리프트와 Windows 시간 보정 중 어느 요인이 기준점 차이를 만들었는지는 분리하지 못했다.

절대 measured_at이 없는 uptime 프레임에 한해 추정 시각이1~5초 앞서면 기준점을 수신 시각으로 재설정하고 거리 이력을 비운다. 부팅/중복/역순/절대 시각/만료 검사는 유지한다. 최종75초 근거 중 **644프레임 모두 프레임 필터 인정, future_frame 거부0회**였다. 좌표 적용은 별도 점프·품질 검사를 계속 통과해야 한다.

## 8. BNO 방향과 낙상 확인

### 방향

기존 방향 센서는10Hz였지만 전송은5초 heartbeat에 묶여 있었다. 별도 최신값 WS 경로로 바꾸고 웹 전체 snapshot 재조회 대신 방향만 갱신했다. 실제12초 관찰에서 **95건,7.95Hz,간격 중앙109.5ms/최대219ms**를 기록했고 사용자가 화살표 회전 추종을 확인했다.

앵커1·4 벽면 기준과 센서 장착 방향을 맞춘 heading offset을 사용한다. 고개 방향과 몸이 걷는 방향은 같지 않을 수 있다.

### 센서 품질0 조사

SH-2 보정 마스크가5(가속도+자기장, 자이로 제외)였고 자이로 비트를 추가해7로 바꾼 뒤 상태0→3을 확인했다. 자기장 기반 Rotation Vector(ID5)는0이 남아, 낙상 상대 기울기는 별도 **Game Rotation Vector(ID8), 상태3**으로 사용한다. 지도 절대 방향 보정까지 해결됐다는 뜻은 아니다.

요청 가속도/자이로50Hz, 자세10Hz. 배터리 재시험 실제 수신은 가속도64.86Hz, 자이로50.11Hz, 두 자세 약10.02Hz였다.

### 자료와 검출 로직

- 정상16회 + 참여자가 실제 낙상이라고 확인한4회. 파일명이 ‘매트 자세 변경’이어도 정상으로 바꿔 분류하지 않았다.
- 정상 숙임 최대45.4~55.0°, 좌우32.2~39.6°, 앉기13.0~15.9°, 걷기9.9~19.6°, 낙상 표본69.6~125.1°.
- 작은 자세 자료를 참고한 **규칙 기반** 후보다. 학습된 낙상 분류 모델을 완성했다고 기록하지 않는다.
- 충격형(kind100): 충격·각속도·자세 변화·이후 안정 상태 조합. 자세형(kind101): 기준 대비60°/3초 등 상태 조합.
- P4 로컬 후보와 서버의 확인 안내 등록은 별개다. 유효 센서 품질·신선도·정상 자세 기준·등록 boot/generation이 맞아야 질문한다.

### 질문·취소·관리자 알림

1. ‘넘어지셨나요? 괜찮으면 괜찮아, 도움이 필요하면 도와줘라고 말씀해 주세요.’
2. 스피커 완료 ACK 이후20초 응답을 기다린다.
3. 호출어 없이 ‘괜찮아/괜찮아요’ → 사건 해소 + 취소 안내.
4. 도움 요청/무응답/질문 전달 미확인 → 각 사유를 구분한 관리자 확인 요청.
5. 통화 중이면 질문을 겹쳐 틀지 않고 관리자에게 낙상 의심을 알린다.

| 실제 확인 | 결과 |
|---|---|
| 음성 취소 재시험 | 질문 종료→worker_ok 1.897초, 사용자가 취소 안내 청취 확인 |
| USB 제거·배터리 무응답 시험 | 질문21:08:01.422→알림21:08:21.439, **20.018초** |
| 위179.61초 동시 구간 | YOLO11.13FPS, 상세3.74FPS, UWB온라인88/88 |
| 질문·대기26.82초 부분 | YOLO9.28FPS. 순간 저하 존재 |

위 손으로 기울인 시험은 연결 흐름 검증이다. 사용자 보고 실제 동작에서는 **2.8331g·2.6514rad/s·66.86° 충격 후보가 잡혔으나 질문 전송 연결이 없어 음성을 듣지 못한 사건**도 있었다. 따라서 ‘실제 낙상을 못 잡았다’와 ‘잡았지만 안내가 전달되지 않았다’를 구분한다. 질문 전달 실패 재시도·실패 후120초 쿨다운 정책은 별도 보완 대상이다.

마지막 P4 업로드 뒤 기준 자세는 초기화됐다. **시연 전 정상 착용 자세 저장과 현재 부팅 세션 재등록이 필요하다.** 원시 가속도·자이로 수집은 기본OFF로 두고 필요한 때만 켠다. 원시 진단은 구간별6.7~24.7% aged 폐기가 관측돼 상시 켜면 부하를 늘릴 수 있다.

## 9. 화재·비상·대피 안내

화재/도움 신고는 STT 결과에서 호출어 없이도 처리한다. 단순 조회와 달리 긴급 이벤트·위치 공유·관리자 연락 요청을 우선하며 LLM 응답을 기다려 신고를 미루지 않는다. ‘요청/전송’은 관리자가 실제 통화에 응답했다는 뜻이 아니다.

대피는 등록한 주 비상구·책상2.4×1.2m·벽/장애물·위험영역과 UWB/heading을 이용해 코드가 계산한다.

- A* 경로 및 상대각: 정면±30°, 뒤쪽150° 이상, 약1.5m 전 모퉁이 예고 등.
- ‘서쪽으로’ 대신 **‘앞으로 쭉 가세요 / 오른쪽으로 도세요 / 왼쪽으로 도세요’**.
- 위치1.5초·방향1초 이상 오래되면 진행 방향 대신 확인 중 안내.
- 장애물 여유25cm, 화재 여유75cm. 지도와 실제 통로 확인을 전제로 한다.
- 경계25cm 안쪽 오차는 최근 통로 이력이 지지할 때만 경로 시작점을 보정. 실제 worker 좌표를 덮거나 책상을 관통하는 선을 추가하지 않는다.
- 점 하나를 완벽히 따라가게 하지 않고 경로 폴리라인과 좌우30cm 추종 범위를 표시한다. 30cm는 시험 허용 오차이지 실제 안전 폭 보증이 아니다.
- 기존 선분·다음 선분 투영, 남은 선분 교차 검사로 관통을 방지한다.
- 전송 최소3초, WAV가 길면 길이+0.5초. 동일 직진/확인 불가15초, 현재 회전6초. 상태 변화는 우선하되 최소 간격 유지.
- 지도 서명이 바뀌거나 새 지도가 적용되면 자동 안내를 다시 확인해야 한다. 무조건 벽에 붙이는 경로가 아니다.

화재 종료 API는 안내 태스크·반복 상태를 지우고 P4 `stop_evacuation`으로 대기·다운로드·재생 루프를 취소한다. 서버·펌웨어에 반영됐지만 종료 버튼→실제 재생 중단 청취의 완전한 시연은 별도다.

실제 출구까지 통제된 모의 보행 완주, 연기·문 잠김·동적 장애물·계단을 자동 인지하는 기능은 검증하지 않았다. ‘화재 발생이나 이런 것처럼’이라는 시험 설명도 신고로 처리된 사례가 있어 인용/설명 문장 구분은 남아 있다. 재난 시 실제 사용 안전성을 검증한 제품으로 소개하지 않는다.

## 10. 위험구역·비인가 진입 경고

활성 danger/controlled/confined 구역에서 작업자 ID가 허용 목록에 없고 새 유효 좌표3회가 안쪽이면 확정한다. 허용 목록이 비어 있으면 모두 비인가다.

- 웹에 즉시 이벤트, 계속 안에 있으면 **구역·작업자별30초** 간격.
- 안전모 이탈 음성. 통화 중에는 웹만 알리고 음성 보류.
- 통화 종료 후에도 여전히 비인가·구역 안·최신 위치일 때만 재생.
- 이탈·허가·삭제·만료 시 보류 취소. 오래된 음성을 연속 재생하지 않음.
- 최대3회 제한 재시도, 동일 command_id, P4 성공ID16개 캐시로 중복 재생 방지.
- 음성 전달은 UWB 입력 경로 밖에서 실행. 대기128개/TTS동시2개 제한.

실제 웹 반복 간격30.055초, 다른 시험30.001초. 사용자가 ‘잘들림’ 확인했고 P4 `zone duplicate skipped`도 기록했다. 최종45.015초 시험 통화에서 음성은 보류됐고 **종료 약0.47초 뒤 명령 전송**, 약9.3초 뒤 스피커 완료 ACK를 받았다. 0.47초는 첫 소리까지의 측정값이 아니다.

완료 후 조회의 현재 등록 구역은 **0개**, 대기 음성0개다. 시험용 구역을 운영 금지구역으로 임의 재등록하지 않았다. 시연 전에 실제 사용할 시험 구역과 허용 작업자를 지도에 등록해야 한다.

## 11. 통화 연결·음질·끊김·폐기 개선

### 구조 개선

초기 P4 `call_tx`4KiB 스택 오류를8KiB로 늘린 뒤에도136/172초 단절이 남아 원인을 분리했다. 서버 수신에서 상대 send를 직접 기다리던 구조를 소켓별 bounded writer로 바꿨다. 용량·age·제어 폐기를 구분하고 오래된 음성을 계속 쌓아 지연을 숨기지 않는다.

Wi-Fi 절전 해제 비교에서는 TX최대1,096.716→44.467ms, 약197초 구간 영상 전송 실패0을 기록했다. 이후 긴 시험에서는 다시 단절·큐 폐기가 나타났으므로 전체 해결로 일반화하지 않았다.

최신 음질 개선:

1. ScriptProcessor2048 중심에서 AudioWorklet·연속 위상 리샘플링·20ms/320샘플 전송으로 변경.
2. 통화 WebSocket을 Dedicated Worker로 옮기고 MessageChannel로 오디오 스레드와 직접 연결. UI/카메라 화면 처리와 PCM을 분리.
3. 브라우저 재생60ms 프리버퍼·200ms 링버퍼, 재생 시간 겹침 제거, 부족/재개 램프.
4. P4 RX큐6→12개(용량240ms), age제한200ms 유지, 시작60ms 준비·무음/복귀 감쇠.
5. 통화 수신만75% 게인, 일반 TTS/마이크 호출 설정은 유지.
6. 카메라 WS버퍼16→64KiB, 라이브러리 송수신 lock 분리, 로그·commit을 비동기/worker로 이동.

### 음질 단계별 실제 수치

| 단계 | 웹 송신 backpressure 폐기 | 웹 수신 overflow | YOLO/상세 FPS |
|---|---:|---:|---:|
| Worklet1차, UI 스레드 네트워크 | 58.31% | 36.85% | 10.40 / 3.53 |
| Dedicated Worker | 0% | 10.44% | 9.54 / 3.49 |
| Worker + P4 RX 최종 음질 시험 | 0% | 11.52% | 8.59 / 3.29 |

최종 음질 시험77.11초의 P4 RX폐기는 약**11.98%**, I2S쓰기 오류0이었다. 사용자는 **‘통화 잘됨’**을 확인했다. 청취 개선과 폐기1% 미만 달성은 다른 판단이다.

이전179.9초 합성 양방향 시험에서는 서버→P4중계0.367%, 서버→웹0.125%였지만 P4내부큐는 약16.5% 규모 폐기가 있었다. 서버 비율만 보고 종단 손실1%미만이라고 기록하지 않는다.

10분 배터리 통화 시험에서는 약29.1초 뒤 채널 단절1회,5.35초 뒤 복구, 이후약9분25초 유지였다. 최신45초 구역 정책 통화는 마지막 회차에 단절이 없었지만 그 직전 비교에는 약0.95초 재연결이 있었다. **장시간 절대 무단절은 미보장**이다.

### 호출어 없는 ‘통화 종료’

안전모 통화 PCM을 먼저 중계한 뒤 별도 제한 작업에서 ‘통화 종료/전화 끊어줘’ 허용 문장을 STT한다. 통화별 실행1+최신대기1, 전체동시2, 1.5초 지난 대기 생략, 요청 제한4초 등으로 부하를 제한한다. 일반 AI대화 전체를 통화 중 계속 실행하는 것은 아니다. 로컬 종료 모델이 아니며 추가 STT비용이 있다. 음성 원문/통화 파일은 저장하지 않는다. 실제 발화 종료·부정 문장 오인식 장기 시험은 남아 있어 웹 종료 버튼을 유지한다.

## 12. 배터리·소비전력·사용시간

배터리 정격 **3.7V·5000mAh ≈18.5Wh**. MAX17048은 SOC·전압 측정용이며 이 구성에서 전류를 직접 재지 않는다. USB가 연결됐다는 것만으로 배터리 소비 W를 정확히 알 수 없다.

순수 배터리30분(15:43:04~16:13:04),5초 간격361표본:

| 10분 구간 | SOC 감소 | 전력 추정 | 완충 사용시간 외삽 |
|---|---:|---:|---|
| 영상·YOLO·UWB·방향·마이크 감시 | 2.6211%p | 2.91W | 6시간22분 |
| 위 + 배터리 TTS20회 | 3.4531%p | 3.83W | 4시간50분 |
| 위 + 합성 양방향 통화 | 4.0664%p | 4.51W | 4시간6분 |
| 전체 혼합30분 | **10.140625%p** | **3.75W** | **약4시간56분** |

SOC53.78125→43.640625%. 계산은 `18.5Wh×SOC감소/100÷시간(h)`다. 별도 전력계로 측정한 W가 아니며 실제 용량·온도·노화·차단 전압·SOC오차를 포함한다. 100→0% 완전 방전 시험은 아니다. 구간 차이를 모두 스피커나 통화만의 단독 소비로 계산하지 않는다.

후속 압축·큐 개선은 USB/충전 연결 조건이어서 새 전력 절감률을 계산하지 않았다. 전송량23.25%감소를 소비전력23.25%감소로 바꾸면 안 된다. 발표 표기는 **‘5000mAh 기준 혼합 부하 약5시간 예상, SOC감소 기반30분 시험 추정’**이 적절하다.

### 로그 설계와 병목 대응

- 영상·음성 trace는 bounded queue512 + writer thread. 로그 실패/폐기/깊이 계측.
- 일반 영상 최신1장·상세별도 프로세스·미리보기 재사용.
- 통화 queue 용량·최대나이·overflow/aged/I2S에러/무음 보강을 별도 기록.
- IMU원시 진단은 기본OFF, bounded 큐/500ms 유효기간, 사건 후보는 별도 보존.
- UWB원시→거리필터→solver→점프판정→정지필터→표시 좌표를 분리 기록.
- Windows 로그 회전 중 파일 잠금 오류를 공유 읽기 방식과 함께 보완.
- 이벤트 루프 watchdog은 정체시 스택 위치를 제한 빈도로 남긴다. 인증값/로컬변수 덤프를 저장하지 않는다.

최종 JPEG페이로드는 약630,400B/s≈5.04Mbps. 통화PCM16kHz/16bit/mono는 한 방향 원본32,000B/s≈256kbps(패킷 헤더 제외)다. 영상은 장면별 JPEG크기가 달라진다. 이 값은 Wi-Fi전체 사용량·재전송·공유기 혼잡 전체를 측정한 것이 아니다.

최종 구역 판단 최대219.73ms, UWB위치 나이 중앙63ms/최대2.186초 기록도 남겼다. 평균YOLO10.20이 나왔어도 지연과 수신 공백이 전혀 없다고 할 수 없다.
